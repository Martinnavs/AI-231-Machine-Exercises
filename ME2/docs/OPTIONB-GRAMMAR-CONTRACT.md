# Option B Grammar Contract

Shared contract for the Option B closed-world spoken-command grammar
(`me2_voicegen.vcm.optionb`). Source of truth for each section is the
module/file named; if this doc and that module ever disagree, the module
wins and this doc is stale and needs fixing.

## 1. `$CMD_*` rules (source of truth: `src/me2_voicegen/vcm/optionb/grammar.py`)

from `docs/raw_requirements/optionb-dataset-readme.md`'s "Phrase variations"

## 2. Slot vocabularies (source of truth: `src/me2_voicegen/vcm/optionb/grammar.py`, `vcm/optionb/numbers.py`)

6 slot vocabularies. `COLOR` and `TASK` are plain word vocabularies (3
values each, no numeric form). The other 4 -- `DURATION`, `ALARM_TIME`,
`DEGREES`, `PERCENT` -- are **numeric slots**: each has **3 values x 2
surface forms** (digit and spelled-out word), sharing one canonical
README-verbatim value per pair. The word form is generated by
`vcm.optionb.numbers.spell_integer` rather than hand-listed (D9/D11) -- there is
no per-value alias table anywhere in this package.

`{time}` is renamed to the internal slot key `ALARM_TIME` (D10), not
`TIME`, because `TIME` is already a fixed-intent name (`$CMD_TIME`) in this
grammar's own namespace; reusing it as a slot key would collide.

| Slot | Values (README-verbatim canonical) |
|---|---|
| `DURATION` | 10 seconds; 30 seconds; 1 minute |
| `ALARM_TIME` | 6 AM; 8 AM; 9 PM |
| `DEGREES` | 18 degrees; 22 degrees; 26 degrees |
| `PERCENT` | 20 percent; 60 percent; 100 percent |
| `COLOR` | red; blue; green |
| `TASK` | drink water; study; exercise |

## 3. Normalization contract (source of truth: `src/me2_voicegen/vcm/optionb/text.py`)

`vcm.optionb.text.normalize_text(text) -> str`: lowercase; fold curly
apostrophes (U+2018/U+2019/U+02BC) to `'`; keep `a-z`, `0-9`, `'`, space;
every other character becomes a word boundary; collapse whitespace; strip.

**`vcm.text.normalize_text` is wrong for this dataset and must not be used
here (D2):** it drops digits, which collapses several Option B slot values
into ambiguous shared buckets once digits are stripped -- e.g. digit-form
"10 seconds" would lose its "10" entirely. Under a digit-preserving
normalizer, all 93 canonical phrases are distinct with zero cross-intent
collisions; under `vcm.text.normalize_text`, 18 of them would collapse into
12 buckets.

Adding word-form (spelled-out) numeric slot values does **not** remove this
requirement: digit forms remain accepted (both forms co-exist in the
grammar), so digit-preserving normalization is still required for those
phrases to survive.

## 4. `accepts()` contract (source of truth: `src/me2_voicegen/common/grammar_core.py`, `vcm/optionb/grammar.py`)

`OPTIONB_GRAMMAR.accepts(text)` walks an already-normalized, single-spaced,
lowercase string through a character trie and returns the terminal
`(intent, slots)` list if `text` is exactly a complete accepted phrase, else
`None`. No fuzzy matching, no partial matches.

**Canonical-93 vs accepted-129:** the canonical set is exactly the 93
phrases the live-upstream README's phrase-variation/slot-value tables
describe, verbatim -- no substitution needed, since `KNOWN_README_DIVERGENCES`
is empty at this refresh:

```
93 = 39 fixed (13 unslotted intents x 3 phrasings)
   + 54 slotted (6 slotted intents x 3 templates x 3 values)
```

The accepted set additionally includes the word-form (spelled-out number)
variant of every numeric slot value, for the 4 numeric-slotted intents only
(`BRIGHTNESS`, `TEMPERATURE`, `TIMER`, `ALARM`; `COLOR` and
`CREATE_REMINDER` have no numeric slot and contribute no word forms):

```
129 = 93 canonical + 36 word-form expansions (4 numeric intents x 3 templates x 3 values)
```

**Closed-world guarantee, no over-generation (D4):** `vcm/optionb/grammar.py`
contains zero occurrences of `opt()`. Every rule is a flat `alt()` of
exactly its fixed phrasings/templates -- there is no optional-word
machinery to accidentally over-generate phrases the dataset was never
recorded with. This holds for the two-surface-form (digit/word) case too:
`_numeric_vocab` emits exactly 2 entries per number (digit form, word form),
never more, so the grammar never accepts a phrase absent from the
93-canonical-plus-36-word-form set.

**Strict-prefix note (D6), now test-enforced, re-derived for this refresh
(never carried over unchanged from a prior grammar):** among the canonical
93, **6 strict character-level prefix pairs** exist (one phrase's text is a
character-for-character prefix of another's) -- `"pause"` is a prefix of
`"pause audio"` and `"pause song"`; `"stop"` is a prefix of `"stop
playing"` (STOP's v1 is now the bare word "stop"); `"time"` is a prefix of
`"timer 10 seconds"`, `"timer 30 seconds"`, and `"timer 1 minute"` (because
"Timer" itself starts with "Time"). Adding the 36 word-form phrases
introduces **3 more** instances of the same "time"/"timer ..." relationship
(`"timer ten seconds"`, `"timer thirty seconds"`, `"timer one minute"`),
for **9 total** strict-prefix pairs among the accepted 129 -- this is a
necessary, unavoidable consequence of the README's own phrasing, not a
defect in the grammar. `tests/test_optionb_grammar.py::test_strict_prefix_pairs_exact_set`
hardcodes and asserts this exact 9-pair set, re-derived by scanning the
actual compiled grammar's `all_phrases()` for this refresh rather than
assumed from the prior (8-pair) count -- the exact staleness mistake this
contract has previously flagged as a trap, not to be repeated.

**Former D1 -- README/manifest divergence (fully resolved upstream).**
A prior refresh found the real dataset's `manifest.csv` disagreeing with the
vendored README on exactly one phrase (`VOLUME_DOWN` v2: manifest said
"Lower the volume", README said "Decrease the volume"). As of this refresh's
vendored commit (§6), the live upstream README itself now reads "Lower the
volume" -- the divergence was corrected at the source, not merely reconciled
locally. `vcm.optionb.grammar.KNOWN_README_DIVERGENCES` is therefore `[]`.

**Dual-anchor drift guard.** `tests/test_optionb_grammar.py` maintains two
independent vendored anchors rather than one:
- **Primary anchor:** `docs/raw_requirements/optionb-dataset-manifest-summary.md`,
  derived from the real manifest's own `transcript` column --
  `test_drift_guard_manifest_matches_grammar` re-derives the canonical 93
  from it and asserts an exact match against both `CANONICAL_93` and
  `OPTIONB_GRAMMAR`.
- **Secondary anchor:** `docs/raw_requirements/optionb-dataset-readme.md` --
  `test_drift_guard_readme_matches_grammar` re-derives the canonical 93 from
  the README and cross-checks it against `CANONICAL_93`/`OPTIONB_GRAMMAR`,
  reconciling any future divergence via `KNOWN_README_DIVERGENCES` (empty at
  this refresh). `test_known_readme_divergences_empty` pins the table to
  zero entries.

Both anchors stay live (neither is deleted or silenced) so that a future
correction to either vendored source -- the README changing again, or a
manifest re-fetch changing something -- is caught by a test failure rather
than by nothing.

**D10 -- CTC-decoder reachability (documented, not a grammar defect).** A
downstream char-CTC decoder path (Task 3/4 territory, not this grammar) has
no digits in its output alphabet. Of `OPTIONB_GRAMMAR`'s 129 accepted
phrases, only the **93 digit-free ones** are reachable by such a decoder --
the 36 digit-bearing phrases are permanently dead branches on that decoder's
character trie. The reachable-93 set and the canonical-93 set are **both
size 93 but are different sets**: canonical-93 includes the 36 digit-form
numeric phrases and excludes the 36 word-form numeric phrases (the reverse
of the reachable set). This makes the grammar's word-form vocabulary
(`_numeric_vocab`'s two-surface-form design, D9) load-bearing for that
downstream path, not merely a convenience: without the word forms, a
char-CTC decoder's spelled-out-number outputs would be ungrammatical by this
contract's own rules.

## 5. Taxonomy divergence from `VCM-CONTRACT.md`

`OPTIONB_GRAMMAR`'s 19-intent taxonomy is unrelated to and never
interchangeable with `vcm.optiona.phrases.INTENT_PHRASES`'s 20-intent taxonomy:

- Option B has no `DIM_UP`/`DIM_DOWN` or `TEMP_UP`/`TEMP_DOWN` split --
  `BRIGHTNESS` and `TEMPERATURE` are each single intents parameterized by a
  slot value, not directional pairs.
- Option B's `COLOR` intent has no VCM counterpart at all.
- Option B's reminder-creation intent is named `CREATE_REMINDER`; VCM's
  equivalent (toy-only, no BNF rule) is named `SET_REMINDER`.

**These two grammars are never interchangeable** -- do not attempt to map
one taxonomy onto the other, reuse `vcm` decoder/model code against
`OPTIONB_GRAMMAR`, or vice versa.

## 7. Representation boundary (D13)

**Verified vocabulary census** (re-derived for this refresh, enumerated directly from
`OPTIONB_GRAMMAR.all_phrases()` and `vcm.optionb.numbers.spell_integer`; the module wins if this
ever drifts -- not copied forward from the prior refresh's count): **90 unique alphabetic word
types** across all 19 intents and all slot values (66 template words + 13 slot unit/value words +
11 spelled-number word tokens -- zero overlap between the three groups; the template-word count
grew from the prior refresh's 56 because the 7 rewritten `CMD_*` rules introduce new words such as
"adjust", "audio", "end", "level", "place", "playback", and "shut"), plus the **12 digit tokens**
(1, 6, 8, 9, 10, 18, 20, 22, 26, 30, 60, 100). Canonical-93 surface token types = 91 (79
non-numeric alphabetic tokens + 12 digit tokens, no spelled-number words); accepted-129 surface
token types = 102 (90 alphabetic + 12 digit).

`OPTIONB_RULES` (and every `CMD_*` alternative list feeding it) is built
entirely out of word-sequence tuples -- `_vocab`, `_numeric_vocab`,
`literal`, `seq`, `alt`, `slot`, `with_intent` all operate on
`tuple[str, ...]` word sequences and never touch characters, phonemes, or
any other sub-word representation. `OPTIONB_RULES` itself is therefore
word-level and representation-neutral.

`OPTIONB_GRAMMAR.root` (built by `compile_grammar`) is a **character**
trie: it inserts each alternative's joined text (`" ".join(words)`)
char-by-char, purely as this feature's own acceptance-check mechanism (no
CTC/decoder involved here, unlike `vcm.decoder`). That representation
choice lives entirely in `compile_grammar`/`Grammar.accepts`, not in the
rules themselves.

This separation means a future phoneme-level lexicon (mapping each word to
one or more pronunciation variants, for a real ASR/decoder integration)
would compose with `OPTIONB_RULES` unchanged -- it would replace or wrap the
character-trie compilation step, not the word-level rule definitions. No
such lexicon exists in this codebase; this section documents the boundary,
not an implementation of it (see the separate deferred-followup ticket
context referenced from ticket 02, not acted on here).

One consequence worth flagging for that future work: although the digit
token `"10"` and the word token `"ten"` are treated as entirely distinct
vocabulary entries at the word/character level (not unified at any
representation layer below the rules), the digit/word homophony this implies
(e.g. "10" and "ten" producing the same phones) is already harmless by
construction, for free -- `_numeric_vocab`'s two-surface-form design (D9)
already assigns both the digit and word surface forms of a numeric slot
value the identical canonical `slots[name]` value before either ever reaches
`OPTIONB_RULES`. A future phoneme-level lexicon therefore does not need its
own explicit digit/word homophony-collapse step here: the collapse to one
canonical value has already happened upstream of any representation choice,
character-trie or phoneme-based.
